# Minimal fresh-seed confirmation of the Rust24-bpk niche

This is a source-only proposal. No compilation, filter construction, calibration or timing has run for these inputs. It reuses the unchanged full336 native executable, including its public Range and Fastbloom adapters and all four query/four build contracts.

The shortlist is derived from the **complete** training table, not from a guessed probe count: for each size2^16/2^25, batch1/31/4096 and all eight metrics, select the fastest external allocation whose actual bytes fit24 bpk and whose independent two-sided95% Wilson upper bound is at most0.01%. Preserve exact ties and take the union. All48 selections independently produce `Fastbloom017K7` at actual24 bpk. `selection.json` retains all eligible alternatives in every decision and60 distinct external size/allocation quality records under the cap. SBBF, Bloomsday, automatic K11/K17 and every fixed K1…12 stay in that supporting record, including all failures; the complete112-record quality document additionally retains32-bpk evidence. No family is silently omitted from the eligibility calculation.

The resulting finite ledger has only12 workloads/24 rows: Range24 plus the selected external union, two sizes, three batch tags and fresh seeds32452843/49979687. Query2^22, independent calibration2^24,50% hits, full-input insertion and eight repetitions remain unchanged. Each row reports all eight metrics, so the proposal does not expand into another completeK Cartesian grid. The second seed reverses workload order. The source-derived API order is opposite between the two seeds for both sizes and all three batches; each seed retains the exact balanced four-query-phase schedule. Seeds were selected before any new filter outputs; they are not selected for FPR or speed.

The frozen producer currently validates the original full-registry training grid. A future additive runner will therefore need a **subset-aware result guard**, while preserving all original per-row geometry/probe, phase/trial, checksum, command and raw-output checks. The executable and timed code need no rebuild. Validate the supported public CLI and guards with tiny fixtures before a separately committed execution freeze; do not repeat the old broad native/sanitizer suites for unchanged code.

Fresh quality is a gate, not a reason to switch K or omit a row. Keep eight unpooled API×size×seed calibration records; batch/mode reuse never enlarges the denominator. Report per-seed qualification and require both seeds to pass the0.01% upper-bound target for a family/size to enter the aggregate qualified comparison. If either shortlisted API fails, retain the failure and every timing; no adaptive replacement, extra seed or measurement extension is authorized by this proposal.

Report all per-seed/batch/query/build wins, losses, exact ties and trial ranges, with separate query contracts and construction boundaries. Build phase order remains fixed and only build medians exist in the unchanged CSV. The primary claim is limited to this24-bpk capacity niche versus the training-derived strongest public external shortlist, at these sizes and seeds. It cannot establish global leadership, cover unmeasured external libraries, or turn the24-bpk advantage into an equal32-bpk claim. The original complete training evidence retains the unfavorable equal-byte Range/Split64 controls and all other public-K results.

Any subsequent integration would expose an optional native public Range type/constructor; this plan does not replace existing default layouts or authorize production edits. CPU placement, exact lock lease and runner/source commit are fixed only in the later reviewed execution protocol. No CPU lease is requested by this proposal.
