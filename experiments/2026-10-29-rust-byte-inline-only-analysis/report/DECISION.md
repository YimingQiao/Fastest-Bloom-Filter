# Minimal Byte hint: evidence and remaining tradeoff

This32-workload/96-row CPU3 experiment preserves the visible-public-API benefit with only the Byte `contains_hash` hint. Production is still unchanged; no extra hint, routing change or padding was introduced. The new binary contains original, triple-hint and one-hint types together, with source-derived reversed pair order over the two seeds.

At batch1, original/one-hint visible prehash and fused-hash geometric ratios are respectively1.5146/1.3779 for small actual16bpk,1.4911/1.3835 for small32,1.2418/1.1569 for large16, and1.2626/1.2356 for large32. All64 retained original/one-hint visible comparisons improve, but repeated batches/modes reuse data and are not64 independent experiments. One-hint and triple-hint visible active AVX2 code is identical; the extra Four/Split hints are unnecessary to obtain this Byte API benefit in this executable.

The bulk regressions remain material to the decision. At32M keys and actual16bpk, generic staged-hash batch3 is about2.64% slower geometrically, and batch31 about2.31% slower; both seeds/order directions lose in both cases. The worst individual original/one-hint ratio is0.968118 for batch3 prehashed, about3.29% slower. Large actual32bpk batch3 is near parity (about0.12% raw and0.21% pure slower), so the earlier15% initial cliff does not recur here. Large actual32 batch31 raw is about0.79% slower. All individual losses, trial extrema and pair directions remain in the tables.

All three public batch functions have the same79 selected active batch3 AVX2 instructions after normalization; their addresses differ. That rules out extra instructions in this particular hot region as an explanation, but does not establish code alignment, allocation placement, cache state or order as the cause. The compact binary registers only Byte types and is not the previous ten-type layout. No performance is compared across binaries or CPUs.

The experiment contains no external rivals and supports no external-leadership claim. Earlier Byte216 measurements and their losses remain intact. Quality contains8 unpooled size/budget/seed records: worst95% Wilson upper endpoints stay below1% at16bpk and0.1% at32bpk, but not0.01% at32bpk. Equal query semantics and byte allocation are checked for all three types. These results support considering the minimal Byte-only API change with the recorded batch tradeoff; they are not a claim that every caller or workload improves.
