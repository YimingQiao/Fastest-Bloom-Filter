# Rust SIMD singleton: proposed internal comparison

This is one finite, source-only proposal for the exact proved SIMD candidate against the exact safe SingleLine control. It includes both native-host and portable-runtime builds because their actual public call boundaries differ. No compiler, Bloom-filter execution or measurement is authorized by this document. There are no external, FPR, build or multithreaded claims.

The fixed grid is 2 build profiles × 2 sizes × 6 hit/batch combinations × 2 new proposed seeds × 2 launch rounds × 2 arms: **96 fresh processes / 192 rows**. Sizes are 2^16 and 2^25 inserted hashes, always 24 actual bits/key (192 KiB / 96 MiB). Every row queries 2^22 keys, using eight query repetitions. Hit 50% covers batches 1, 3, 31 and 4096; hit 0%/100% adds batch 1 only. Both arms in a process receive the same complete workload. Seeds 6812364731 and 9517218469 are fixed before execution. `ledger.json` gives the exact order and source-derived raw-counter envelopes, which are mutually disjoint and disjoint from the tiny proof's envelope; these are not observed input digests or evidence of statistical independence.

Round 1 uses the recorded profile/size/seed/case order and Control then Candidate. Round 2 reverses the entire 48-process ledger and every arm order without consuming RNG. The same input therefore sees both API orders. The four-mode Williams schedule and two-mode ABBA schedule repeat twice per row, retaining equal mode positions. All raw phase orders and samples will be retained. Neither seed nor round is treated as an independent replicate for a global win rate; round is also environmental history, not an isolated order intervention.

Batch 1 retains generic pure, generic hash+query, optimizer-visible pure and optimizer-visible hash+query. Other batches retain the two generic contracts. This yields **288 paired metric contrasts, 576 eight-trial vectors, 4608 values, 144 opposite-round sensitivities and 72 four-point seed×round ranges**. The 224 contrasts for batches 1/3 exercise the changed paths. The 64 batch 31/4096 contrasts are controls whose original bulk kernels remain source-identical; the added public dispatch and rebuilt machine-code layout may still affect them. With q=2^22, batch31 ends with four keys, so it does not incidentally exercise the new 1–3-key tail route.

An additive formal caller must be prepared and reviewed before any build. The existing check-only caller remains immutable. Preserve `query.rs`, the common hash, trait forwarding and both complete native module closures exactly; do not add inline hints or alter target features. Parameterize only fixed workload/loop bounds, metadata and explicit formal CLI/arm order. Keep the timed start→public work→stop block byte-exact, with dynamic bounds introduced outside it; repeat schedule indexing occurs outside clocks. Record a precise patch and hot-source equality checks. The current hard-coded check constants mean this is a new caller build, not reuse of the proof executable. Rebuilt native/portable ELF address/size and actual public/clock boundaries must be inspected again; do not assume prior addresses or identical code generation.

The bounded derivative proof should reuse the already-passed kernel/oracle matrix, not repeat it. Proposed caller-only coverage is each of the two profiles at the seen tiny seed74381/n256/q4096/hit50 with batches1/3/31/4096 (16 rows), plus reversed-arm batch1 in both profiles (4 rows), eight invalid CLI rejections and the four existing skip/wrong-output faults. Match the original immutable proof's complete semantic fields for these inputs, not timing values. Native and portable must both report actual AVX512 execution on the selected host; portable runtime dispatch is not a forced scalar baseline. No new ASan kernel run is proposed because the exact kernels and hot query body already passed; any broader source delta requires review of that assumption.

Each formal arm builds once outside clocks and fully checks its bitmap against the independent oracle and every inserted key. All query outputs are poisoned and completely compared after every timed phase; guards, immutable inputs and complete bitmap are checked outside clocks. Scratch, independent bitmap/reference output and input copies are allocated before timing and retained equally for both arms; only one tested filter lives at a time. The two profiles are analyzed separately using within-profile candidate/control latency ratios. Input/bitmap/output fingerprints must agree across arms, builds, rounds and batches where the workload is identical; bitmap/insertion identity additionally spans hit rates. Fingerprints are not archived full arrays.

Freeze the final caller, actual binaries, source/tool/input closure, exact command ledger and analysis import closure before formal launch. Analyze only committed complete raw data. For every metric retain median candidate/control latency (<1 favors candidate), all ties and losses, all eight samples, opposite-round results and four-point ranges; do not replace a failed point or filter bulk regressions. No pooled speed summary, comparison to historical C++ times, new calibration or automatic production promotion is planned.

Both profiles will use CPU3/socket1/NUMA1. The entire build/proof or formal operation must inherit an already-held exclusive `/tmp/fastest-bf-socket1.lock`; parent affinity and child CPU3/NUMA1 binding are checked and recorded. No overlapping performance operation is allowed. This is a fixed placement policy, not a current lease grant. Rebuilt executable identities and actual command/proof freezes remain pending.

`SOURCE_REFERENCES.json` binds the proposal, exact old caller and completed proof to immutable Git blobs. `SEED_SCOPE.json` records the fixed repository tip and explicit tracked protocol/ledger/plan files searched for the two proposed decimal seed tokens. This is only a bounded freshness check in that disclosed artifact scope; it does not establish global novelty, random-stream independence or independence between shared-input contracts.
