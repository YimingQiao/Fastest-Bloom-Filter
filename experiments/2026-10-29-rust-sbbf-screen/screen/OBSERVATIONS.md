# Interpretation and limits

All 12 workloads and 168 rows passed exact registry, workload, allocation and semantic guards. The source/binary freeze remained unchanged. The report contains 288 ranked track/setting combinations, 576 individual native comparisons, 504 API ratios and 28 family/size calibration records. The latter remove repeated API and batch results; they are not independent statistical samples across families because every family uses the same keys and negative queries.

The added SBBF implementation does not displace Bloomsday as the best external in this screen. Their complete output checksums and calibration counts match in all 12 workloads, as expected for these two implementations of the same split-block mapping. At 65,536 keys and actual 16 bpk, SBBF's singleton control takes 4.227 ns prehashed / 6.808 ns with hashing, compared with Bloomsday's 3.241 / 5.779 ns. Those results describe public API paths including SBBF's retained dynamic dispatch; this screen does not isolate the cost of the underlying AVX2 probe.

With original native APIs against the best measured external public path, 23 of 30 eligible prehashed cap/ceiling settings and26 of 30 eligible raw settings favor a native layout. These settings reuse the same workloads and nested caps, so they must not be presented as independent wins or a statistical success rate. Small-table singleton losses remain: actual 16 bpk/1% has native ByteSplit 3.633 ns versus Bloomsday 3.241 ns;32 bpk/0.01% has native Split64 4.078 ns versus Bloomsday 3.244 ns. Large-table singleton prehash also loses at loose and strict ceilings. All losses and weaker family results remain in the machine-readable report.

The actual 16/32 bpk grid is intentionally narrow. Upstream SBBF accepts 32 B logical blocks (64 B backing-allocation rounding), Fastbloom accepts 8 B words, and Bloomsday supports intermediate integer-bpk capacities. This screen does not exhaust finer external memory/FPR tradeoffs such as 12/14/24/28 bpk. Eligibility is based on pointwise two-sided 95% Wilson upper endpoints; no simultaneous or selection-adjusted coverage is claimed.

This is CPU3 seed42 exploratory data, not a held-out confirmation. Min/max query trials are descriptive. The frozen harness measures pure queries before hash-plus-query within each repetition; it does not balance those phases. The separate Rust visible-singleton experiment is designed to report the optimizer-visible public API contract and balanced four-mode repetitions without rewriting these results. No production source or previous binary was changed.
