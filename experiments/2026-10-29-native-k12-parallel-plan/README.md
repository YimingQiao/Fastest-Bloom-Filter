## Track A: shared pinned query executor

All49 points run on the same eight-physical-core executor, with caller counted as worker0 and seven spawned workers. Each worker processes complete4096-key batches through the concrete filter's public serial `Lookup` API. Pure queries and common-hash-plus-query use the same compiled lookup kernel; hash work stays inside each worker's timed loop. Thread launch, affinity, synchronization and join retain the existing separately reported boundaries. All families receive the same optimizer/ISA and executor opportunities.

Each row builds one complete bitmap serially, validates every inserted key and warms complete query output. Construction is setup only: no repeated build tax or construction ranking in this track. Eight query repetitions use the seeded balanced four-phase schedule for direct serial pure, direct serial hash, pinned parallel pure and pinned parallel hash. Each four-trial block gives every phase every position once and every ordered adjacent pair once. Every timed output, dense0/1 convention, input/guard and checksum is validated outside clocks. Both gated and end-to-end parallel timings and every trial remain visible. The new phase order is distinct from the older fixed-phase142 screen; old times are never mixed with new ones.

Three seeds ×49 configurations gives147 query rows. Rank each seed separately under actual-byte caps16/24/32 and FPR ceilings1%/0.1%/0.01%, for all four T8 query metrics:216 nested views. Also retain72 all-three-seed-gated conditions without pooling any negatives. The old sources select competitors only; they do not supply new eligibility. All147 API/geometry/seed calibration records remain; proven aliases may reuse a checked mapping identity but never inflate its denominator. All quality failures, unavailable comparators, slower families and unconditional times remain. Native portfolio, production-only and each optional family are separate ownership views. Ratios are candidate/rival latency, lower is faster.

## Track B: actual native public APIs

A separate native-only track measures the real `InsertParallel` and `LookupParallel` entry points, not a thin wrapper that recreates their policy. It includes K12 and Range at actual16/24/32 plus production Split64 at16/32, at both sizes:16 size/geometry points ×three seeds=48 rows. Requested T1/T8 are passed inside the measured call; actual worker counts and scratch are recorded. Six paired repeats alternate which worker count runs first, so each occupies each position three times.

Each construction observation uses a fresh empty filter. Record both insert-only and allocation-plus-insert latency from that same operation; partitioning, counters, scatter, temporary allocations and thread creation/join remain charged. Destruction and full correctness checks stay outside the timer. No populated/streamed performance scenario or extra worker-policy candidate is added. The independently checked parallel construction and subsequent queries must reproduce the serial reference outputs; full bitmap comparison is additionally available for the Range/K12 wrappers with public `Data()` access. Never invent private access for Split64.

Queries call the actual `LookupParallel(q, prehashed_input, output, T)` once per observation. This native API divides full input slices rather than the common executor's fixed4096 batches. Its whole-call end-to-end timings are reported separately from Track A; they must not replace Track A in external leadership rankings. The public wrappers inherit the same eight-core mask but do not pin individual workers. No raw-hash or isolated-gated claim is made for this track. Complete output checks and all inserted-key checks remain outside clocks. Quality is the identical construction's Track A record, reused without adding samples after semantic agreement; failure cannot be repaired by changing geometry or seeds.

There are no external rows in a parallel-build victory panel: the selected public external APIs offer serial construction, and timing those as though they were T8 implementations would misstate the comparison. This stage establishes native K12 build/query behavior against accepted Range and Split64 controls only. T3/T7/non-divisible ownership already has correctness evidence; no additional performance grid over those counts is proposed.

## Boundaries before execution

The complete proposed scope is195 process rows:147 fair shared-executor query rows and48 native API rows. Track A has147 separate API quality observations; Track B adds no quality denominator. The same-host socket, eight physical cores and NUMA node must be fixed and recorded before source freeze. There is no CPU lease or automatic execution in this proposal.

Implementation should copy the existing checked executor/workload and strong exact-budget adapters into one isolated caller, with the pinned actual native headers. It needs only minimal caller/registration/output/geometry checks for new native types and the new phase schedule; the passed kernel matrix is not repeated. The current native compiler/ISA and final consumed source closure must be frozen before data. A fixed seeded configuration order, all commands, all timing vectors, constructor arguments, actual backing and scratch remain in the archive. Externally concurrent readers use one immutable fully built bitmap; concurrent mutation is outside both tracks. Source/binary review and a separate explicit performance lease are still required.
