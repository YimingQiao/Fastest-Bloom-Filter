# Initial raw8 public-API training proposal

This is a source-only proposal for the already-proven actual raw caller. It
does not authorize a formal process. The normal executable from proof73ff8ed
would run18 fixed processes/786 rows: all262 catalog geometries at query
batches1/31/4096, including every one of144 new public fastbloom-rs K1..24
geometries. No accuracy or speed result removes a configuration.

The fixed training settings are n2^16/2^25, requested16/24/32bpk, q2^22,
hit50%, seen seed42, eight trials per metric, and one cal2^24 per geometry.
Only the first query batch1 process calibrates; batches31/4096 use cal0.
Query batch is
independent of **insertion batch4096**. This bounds common-hash build scratch
at32KiB; direct raw8 scratch is0. It is a fixed capacity choice before data,
not a claim that4096 is the best insertion batch. Actual bitmap bytes and
required build/query caller bytes remain distinct.

The two query metrics are raw batched public API and raw visible public
singleton loops. All mandatory hashing is inside each operation; there is no
identity-copy phase or prehash-only label. The two build metrics are raw insert
after readiness and `allocate_filter_and_scratch_raw_insert`, whose start
precedes scratch allocation/initialization and public filter construction.
Every build uses the whole inserted set, in fixed4096-key chunks. Build and
canonical scratch lifetimes, untimed output poison and full output validation
are the unchanged proven caller behavior.

`derive.py` obtains the catalog, actual caller and proof from exact Git blobs.
It computes the real workload draw count, including2,097,154 positive RNG draws
for q2^22/hit50, and records the actual filtered-registry shuffle for every
command. Its O(1) RNG-state skip is checked against literal iteration on small
fixtures. The query phase schedule is the unchanged seeded AB/BA/BA/AB cycle,
repeated twice. API order is a single training permutation and is not fully
balanced; no new source reversal or alternate seed is silently introduced.

Each size has one inserted interval, one envelope containing all timed raw
negatives, and a disjoint calibration interval. Requested budgets/query batches
reuse that input. Different sizes are not asserted independent merely because
their sizes differ. The262 calibration-bearing rows provide262 per-API records;
the524 cal0 rows link to those records only after all frozen geometry, raw-hash,
input and mixed-output identities match. The ledger lists every required field,
source case and reuse case. Cal0 rows must emit zero calibration counts; absent
or failed source records cannot be silently borrowed from another construction.
Complete outputs are checked inside each process; emitted full-output checksum
and counts are cross-process fingerprints, not archived arrays. Only the two
proven default16/K11 Fastbloom0.17
aliases may yield260 mapping identities, after exact current semantic checks.
No cross-family equality is presumed and no sample is pooled.
The fixed cal24 resolution may leave a strict boundary unresolved, including
native K12. An upper bound crossing the target is this finite precision gate's
failure, not proof of a permanently ineligible algorithm. Retain the point and
address close cases in a later prespecified uniform confirmation, without
extending only selected failures after seeing this screen.

Analysis would keep both query and both build contracts separate. For each
size/batch, all actual allocations under each16/24/32bpk cap compete at Wilson95
upper gates1%/0.1%/0.01%, including smaller allocations. There are108 query and
108 build views,28,296 individual alternatives and15,552 new raw8 alternatives.
Keep production native, optional Range, optional K12, retained external and new
fastbloom-rs ownership explicit; record every loss, tie, quality failure and
no-comparable outcome. Build trials remain per row, with query-batch tags; they
are not pooled as repeated independent build experiments. Batch1's additional
post-timing calibration changes subsequent cache/thermal history; this single
training execution order does not isolate that effect or prove batch parity.

The future runner must bind the proof/binary/dependency hashes, actual inherited
CPU2/socket0 flock and CPU affinity, reject unfrozen environment overrides,
verify exact order/49-column schema/all trial medians/ranges/geometry/scratch,
and compare semantic identities across batches. It must preserve every failed
command and final raw stdout/stderr, and keep `cases` as a list with a distinct
case count. A completed raw archive must be sealed before numerical ranking.
Every measured child uses the recorded `/usr/bin/numactl --physcpubind=2
--membind=0` prefix. CPU2 lies on node0; node0 memory binding is an explicit
requested policy, not inferred from CPU affinity. `PLACEMENT.json` pins the
available tool's bytes and its read-only hardware output. The formal runner
must recheck that identity, retain the exact child command and reject placement
errors; requested policy is not retrospective evidence of measured residency.
This placement is fixed before data and waits for the explicit completion,
seal and release of the Poppy run. It uses the same proved normal executable;
the CPU3 correctness proof contributes no latency to this CPU2 screen and no
cross-CPU ratio is formed. The earlier uncommitted pinning-only wording was
corrected before any formal execution.

Poppy is not present in this frozen executable. No incomplete Poppy data was
read or used. This panel can compare the named registered families only;
[POPPY_BRIDGE.md](POPPY_BRIDGE.md) makes completed-evidence inclusion and a new
common-contract confirmation mandatory before a broader strongest-external
claim. The old raw/batch values and old FPR counts cannot be imported into this
new raw8 comparison.
