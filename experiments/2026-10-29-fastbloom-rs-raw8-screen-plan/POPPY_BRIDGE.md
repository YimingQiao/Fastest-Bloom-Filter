# Completed-Poppy confirmation bridge

No current Poppy raw or partial result file is an input to this proposal. The
current raw8 executable is closed and already proved; adding Poppy changes its
dependency graph and actual caller and therefore requires a new isolated source
snapshot and focused actual-caller proof. It is not a relabeling of old timings.

Before any broader strongest-external claim, wait for all36 Poppy processes /
486 rows, the producer's final audit, exact raw manifest and a committed complete
analysis. A later additive selector will first verify those immutable commits
and reconstruct the complete table. It will take the union of **every tied
qualifying Poppy leader** across both sizes, all three query-batch tags,
actual16/24/32bpk caps, all three FPR targets, both recorded rounds and all eight
old query/build contracts. It will retain the exact real-n constructor, public
Space/None/cache policy, actual bucket-plus-cache allocation, and all tie
identities. No seed, requested false-positive parameter, K or geometry is tuned.
Rows that win only one old contract or one round cannot be omitted. The union
size and each provenance view will be published before any new measurement.

Use all eight completed contracts for this bounded leader union because the
old raw/build clock boundaries and preparation are not identical to the new
two-query/two-build raw contract. Old winners are a finite strong shortlist,
not proof that every old losing geometry must stay slower on a new raw stream.
The complete47-API source catalog and all old failures stay linked. If a broader
claim needs all47 configurations, expanding the panel requires a separate fixed
pre-data ledger, never silent omission or a speed-selected follow-up during a run.

The future Poppy source audit must cover **both** natural public input forms:
`raw.to_le_bytes()` through `insert_bytes` / `contains_bytes`, and original
typed-u64 values through public typed membership. The upstream byte8 first-hash
identity path and typed-u64 `PoppyHash` default internal hashing are distinct
mappings with distinct quality records. Neither receives a gratuitous native
common hash. A potentially stronger typed public path must not be omitted just
because the byte8 path clusters for this sequential raw-key domain.

For every chosen geometry, retain both public input forms or explicitly freeze
the complete source-defined coverage decision before the new confirmation.
The old completed byte8 performance ledger cannot establish a best geometry
for the previously unmeasured typed mapping. Preserve each public insertion
Result check, all required internal hashing/cache work, zero common-hash
scratch, and actual buckets-plus-cache backing. Full bitmap/public-output and
allocation/lifetime proofs must cover both new raw-input mappings. Existing
common-hash controls and fastbloom-rs direct APIs retain their real operations.

The new shared raw-only caller must keep the current complete-build scratch
boundary, both query contracts, poison/full outputs and all quality failures.
Include the complete-table winner union from the initial raw8 panel across the
same caps/thresholds/contracts, separately retaining all production/optional
and external owner leaders and all ties. Retain the relevant self-baselines.
Freeze a finite fresh-seed/order-balanced confirmation ledger, uniform quality
sample budget and the combined dependency graph before data. Reuse no old
latency or calibration count: changed input transformation changes the bitmap
and must be measured/qualified anew under the common raw-key contract.

Report original training outcomes and the completed-Poppy confirmation
separately. Until that bridge is proved and measured, say only which registered
family/configuration wins in this initial raw8 panel; do not call it the
strongest Rust external implementation or a global winner.
