## `fastbloom-rs`: exact m/K, separate raw-key contract

This is a different project from the already measured `tomtomwombat/fastbloom`0.17.0. The pinned public builder stores supplied m/K and marks the configuration complete; the normal n/FPR constructor rounds m up to a machine-word multiple and uses `ceil(m/n*ln2)`. `BloomFilter::new` allocates `m >> 6` words on64-bit targets. An adapter must enforce word-multiple m: the explicit constructor itself does not round or reject a nonmultiple, so passing one would leave the modulo domain larger than the allocated bitmap. [Builder](https://github.com/yankun1992/fastbloom/blob/ea18d38eca9cb3a48f395f28ab67004b6f1ab83e/fastbloom-rs/src/builder.rs#L27-L105), [allocation](https://github.com/yankun1992/fastbloom/blob/ea18d38eca9cb3a48f395f28ab67004b6f1ab83e/fastbloom-rs/src/bloom.rs#L147-L155), [vector](https://github.com/yankun1992/fastbloom/blob/ea18d38eca9cb3a48f395f28ab67004b6f1ab83e/fastbloom-rs/src/vec.rs#L14-L26).

The hot public methods hash the actual byte slice with XXH3-64 seeds0 and32, reduce each modulo m, then probe `(h1+i*h2)%m` globally. `get_hash_indices` allocates a K-element `Vec<u64>` and `contains_hash_indices` accepts that already reduced index vector. There is no matching public index-vector insertion in `Membership`; it would be misleading to substitute this one-sided K-word query input for the shared one-u64 prehash contract or exclude its computation/allocation. Keep the normal byte methods as a raw8-byte-key track, including both upstream hashes. The bitmap-slice getters borrow storage. [Hot methods](https://github.com/yankun1992/fastbloom/blob/ea18d38eca9cb3a48f395f28ab67004b6f1ab83e/fastbloom-rs/src/bloom.rs#L12-L121), [trait](https://github.com/yankun1992/fastbloom/blob/ea18d38eca9cb3a48f395f28ab67004b6f1ab83e/fastbloom-rs/src/lib.rs#L13-L26).

Its explicit m/K constructor internally fills a derived expected-elements metadata field. That value must not replace the benchmark's real n. Allocation instrumentation should confirm the one live bitmap and actual requested bytes; no serialization copy is needed.

## Poppy V2: a distinct4KiB-block family

The bucket is4096 **bytes**, not64 bytes. The address is xorshift-star(h1), reduced by bucket-count masking or modulo. Probe0 uses h1; probe1 lazily obtains h2 through a fixed-seed WyHash of h1's big-endian bytes; later probes update h1/h2 and mask into32768 bucket bits. All hash state is64-bit. `insert_iter` tracks count and can return `TooManyEntries`; every insertion Result must be checked. Public `insert_bytes/contains_bytes` on an8-byte little-endian encoding of the common prehash preserves that full h1, while retaining the mandatory internal h2 work. Passing a Rust `u64` through the generic default `PoppyHash` implementation instead hashes it again; those two public APIs are not interchangeable. [Mapping and iterator](https://github.com/hashlookup/poppy/blob/992a13e27e8b09b2a832333a4ba3d160545fa866/poppy/src/bloom/v2.rs#L18-L127), [public methods](https://github.com/hashlookup/poppy/blob/992a13e27e8b09b2a832333a4ba3d160545fa866/poppy/src/bloom/v2.rs#L357-L519), [byte versus integer hashing](https://github.com/hashlookup/poppy/blob/992a13e27e8b09b2a832333a4ba3d160545fa866/poppy/src/hash.rs#L34-L63).

For `None`/`Space`, bucket capacity is derived from fixed32768 bits and requested FPR, bucket count is `ceil(real_n/bucket_capacity)`, and K is derived from that bucket capacity. `Speed` adds a `next_power_of_two(real_n)`-bit index cache and rounds bucket count up to a power of two; `Best` adds the cache without that bucket rounding. Both also change the derived K. These public policies must be separate configurations, not silently replaced by `None`. A future exact-cap plan can use only public n/FPR/options with real n fixed, charge every resulting bucket and cache byte, and reject over-budget outcomes. There is no ordinary independent K setter to pretend otherwise. [Public Params](https://github.com/hashlookup/poppy/blob/992a13e27e8b09b2a832333a4ba3d160545fa866/poppy/src/bloom.rs#L130-L173), [constructor](https://github.com/hashlookup/poppy/blob/992a13e27e8b09b2a832333a4ba3d160545fa866/poppy/src/bloom/v2.rs#L281-L332).

`size_in_bytes()` accounts for bucket bytes plus the cache, but excludes arbitrary attached `data`; a fresh filter leaves `data` empty. Actual vector capacities and allocations still need observation. The CLI's parallel writes copy the filter into each job and later merge; that is a separate replicated-bitmap memory/build contract, not evidence of a public in-place atomic insertion API. [Array storage](https://github.com/hashlookup/poppy/blob/992a13e27e8b09b2a832333a4ba3d160545fa866/poppy/src/bitset/array.rs#L1-L16), [cache allocation](https://github.com/hashlookup/poppy/blob/992a13e27e8b09b2a832333a4ba3d160545fa866/poppy/src/bitset/vec.rs#L1-L14), [reported size](https://github.com/hashlookup/poppy/blob/992a13e27e8b09b2a832333a4ba3d160545fa866/poppy/src/bloom/v2.rs#L535-L537), [CLI memory statement](https://github.com/hashlookup/poppy/blob/992a13e27e8b09b2a832333a4ba3d160545fa866/README.md#L79-L84).

## `bloomfilter`: account for its serialized header

A budget B can use payload B−45 bytes, with real n passed unchanged and an explicitly recorded deterministic32-byte seed. `len()` reports payload bits, whereas `as_slice()` includes the45-byte header. The normal constructor allocates one zeroed header+payload vector. `from_slice` and `to_bytes` copy; `into_bytes`/`from_bytes` move that vector. Inline SipHasher states do not add a second bitmap allocation. [Constructor](https://github.com/jedisct1/rust-bloom-filter/blob/b429a01987fe1a5042d9a28800fde8dfaa4759d5/src/lib.rs#L60-L86), [header/allocation](https://github.com/jedisct1/rust-bloom-filter/blob/b429a01987fe1a5042d9a28800fde8dfaa4759d5/src/bitmap.rs#L4-L20), [import/export](https://github.com/jedisct1/rust-bloom-filter/blob/b429a01987fe1a5042d9a28800fde8dfaa4759d5/src/bitmap.rs#L82-L140).

Public hashing clones seeded SipHasher13 states for probes0/1, then uses wrapped64-bit double hashing with the large64-bit-prime reduction and finally modulo m. Feeding a prehashed u64 to `check` still performs upstream hashing; it belongs in the raw-key track. There is a possible **separate serialized-configuration control**: public `into_bytes` followed by changing the pinned format's K header and public `from_bytes` can retain one bitmap allocation. However, upstream calls this representation opaque; it is not a normal named K constructor and must not be disguised as one or used without dedicated format/semantic validation. No such control was built here. [Public query/hash/K](https://github.com/jedisct1/rust-bloom-filter/blob/b429a01987fe1a5042d9a28800fde8dfaa4759d5/src/lib.rs#L133-L179), [K and double hash](https://github.com/jedisct1/rust-bloom-filter/blob/b429a01987fe1a5042d9a28800fde8dfaa4759d5/src/lib.rs#L293-L316).

## Queue recommendation

1. **Poppy V2 public byte APIs**, because they add a new4KiB-block/cache policy and a compatible full-u64 prehash input via8-byte slices. First prove real-n capacity accounting, all insertion Results, and the public policy geometry; no speed prediction.
2. **`fastbloom-rs` raw8-byte APIs with exact m/K**, because they add a distinct implementation with straightforward bounded public configuration. Keep its internal two-hash work in the raw-key measurement.
3. **`bloomfilter` deterministic raw-u64 API**, accounting for45 header bytes. Start with the ordinary real-n constructor; any serialized-K experiment gets a distinct label and correctness proof.

None needs a private query kernel. None is established here as faster or slower. The current staged-prehash columns cannot simply absorb the latter two normal APIs without falsely removing their required hash work; a declared common raw-key comparison is required. No implementation or CPU lease is requested by this audit.
