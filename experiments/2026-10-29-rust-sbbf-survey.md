# Rust SBBF baseline and concurrent-build audit, 2026-10-29

Status: source audit only. No adapter, compilation, accuracy sweep, or performance run was performed for these new candidates. Existing frozen benchmark binaries and native sources are unchanged.

## Recommended next baseline

Add **sbbf-rs-safe 0.3.2 backed by exactly sbbf-rs 0.2.8**, then an optional direct `FilterFn` ownership adapter as a wrapper-cost control. They share one algorithm and must not be counted as two independent filter families. Both accept already-hashed `u64` values directly; neither applies another source hash. The safe wrapper is small and its insertion/query methods are `inline(always)`. Its underlying kernel is selected at construction and called through a trait object. This is a useful independent Rust implementation of the standard 32-byte Parquet split-block layout, alongside the existing Bloomsday baseline. No speed ranking follows from this audit. [safe public source](https://github.com/ozgrakkurt/sbbf-rs-safe/blob/d5e029a61c68b55cd4f241c0ae35ce06602825f2/src/lib.rs), [kernel public source](https://github.com/ozgrakkurt/sbbf-rs/blob/8ad214f2e3290fa9bbfeb90704c7bf24ee4e88ce/src/lib.rs).

### API, sizing, and hash contract

The safe public methods are `Filter::new(bits_per_key, num_keys)`, `insert_hash(&mut self, u64) -> bool`, `contains_hash(&self, u64) -> bool`, and byte serialization/reset methods. There is **no public batch insert or query**. The direct public API is `FilterFn::new()`, then unsafe `insert(ptr, num_buckets, hash)` / `contains(ptr, num_buckets, hash)`, plus `which()`. It requires a nonzero bucket count and a 64-byte-aligned allocation with at least `32 * num_buckets` accessible bytes. [API documentation](https://docs.rs/sbbf-rs/0.2.8/sbbf_rs/struct.FilterFn.html).

The safe constructor computes `floor(bits_per_key * num_keys / 8)`, rounds that up to 32 bytes, and enforces one minimum 32-byte block. Its allocation then rounds that logical length up to 64 bytes. Therefore `as_bytes().len()` can underreport the requested backing allocation by 32 bytes. At our power-of-two byte budgets, `Filter::new(8, budget_bytes)` creates exactly `budget_bytes` of bitmap and backing allocation without a temporary serialization buffer. The second argument is used only for sizing; it does not change hashing or probe count. An adapter should validate bounded arithmetic first, check logical length, report `align_up(logical_len, 64)`, and verify allocation size independently in a correctness build. It should not infer memory from the nominal requested bpk. [constructor and allocator](https://github.com/ozgrakkurt/sbbf-rs-safe/blob/d5e029a61c68b55cd4f241c0ae35ce06602825f2/src/lib.rs).

There are eight fixed probes, one in each 32-bit lane of a 32-byte block. For a supplied 64-bit hash, the block is `((hash >> 32) * num_buckets) >> 32`; lane positions are the high five bits of wrapped low-32-bit multiplication by the standard eight Parquet salts. This consumes both halves of our common source hash and supports non-power-of-two block counts. Our fixed common budget remains preferable to changing memory to match a nominal target FPR. Measure independent held-out false positives and Wilson bounds; equal byte budgets do not imply equal FPR to native Split64 or ByteSplit. [x86 implementation](https://github.com/ozgrakkurt/sbbf-rs/blob/8ad214f2e3290fa9bbfeb90704c7bf24ee4e88ce/src/arch/x86.rs).

### ISA and strongest public controls

On x86/x86-64, construction selects AVX2, otherwise SSE4.1, otherwise scalar, using `cpufeatures`. Little-endian AArch64 selects NEON; other targets use scalar except explicitly enabled little-endian WASM SIMD. There is no AVX-512 path. The implementation types and trait are private: importing a private AVX2 body into an adapter would change the upstream public contract. A generic Rust build on an AVX2 host still selects AVX2, so removing `target-cpu=native` is **not** a scalar-backend test. Record `FilterFn::which()` or the safe filter's Debug string. Our native `disable-avx512` feature does not disable this dependency's AVX2. [dispatch source](https://github.com/ozgrakkurt/sbbf-rs/blob/8ad214f2e3290fa9bbfeb90704c7bf24ee4e88ce/src/arch/mod.rs).

The integration should retain these separately named controls:

1. `SbbfSafePinned`: exact safe public insert/query calls in the existing batch wrapper, dense `u32` answers, existing timer/checksum/calibration contract.
2. `SbbfSafeSingleApiV1`: length-one direct public `contains_hash`; otherwise the original wrapper. This matches the existing Bloomsday/Fastbloom singleton controls and must not replace their originals.
3. Optional `SbbfDirectPinned`: one owned aligned buffer and the unmodified public `FilterFn`, same bytes, bitmap, outputs and calibration as the safe row. This isolates ownership/wrapper cost, not a new algorithm. Do not invent an upstream bulk API or silently bypass dynamic dispatch.

For each path, inspect generated code before attributing a gap to dynamic dispatch; LTO may or may not devirtualize the stored trait object. Preserve all source/API controls in one process and randomize filter order. The upstream Criterion benchmark repeatedly queries one fixed key and constructs from only 1,000 possible hash values; it does not establish speed on our full independent hash stream. [upstream benchmark](https://github.com/ozgrakkurt/sbbf-rs/blob/8ad214f2e3290fa9bbfeb90704c7bf24ee4e88ce/benches/bench.rs).

Useful correctness gates: complete bitmap equality against an independent Parquet oracle; no false negatives; full dense-output parity across tails and offsets; exact safe/direct parity; minimum/odd block counts to exercise 32-byte allocation padding; allocator accounting; repeated/colliding hashes. Source inspection found the SSE insertion return-value check occurs after updating its first 128-bit half, so its “previously contained” boolean can overstate prior membership. The insertion still ORs both halves and normal membership semantics are unaffected. Our adapter discards that boolean, as it does other insertion status values; do not claim that status API was validated. No code patch to upstream is proposed. [SSE insertion](https://github.com/ozgrakkurt/sbbf-rs/blob/8ad214f2e3290fa9bbfeb90704c7bf24ee4e88ce/src/arch/x86.rs).

### Multithreading scope

`sbbf-rs-safe::Filter` implements Send and Sync and accepts only `&mut self` for insertion. It supports concurrent immutable queries after construction. Neither package supplies atomic insertions or a public parallel builder. A line-owned custom parallel builder would be an adapter implementation, not upstream native concurrent support, and should be a separately declared experiment if ever added. `FilterFn` itself lacks Send/Sync because its trait object lacks those bounds; prefer the upstream safe wrapper for the first read-parallel baseline. [safe ownership declarations](https://github.com/ozgrakkurt/sbbf-rs-safe/blob/d5e029a61c68b55cd4f241c0ae35ce06602825f2/src/lib.rs).

## Follow-up concurrent baseline: Fastbloom 0.17.0

The already-pinned Fastbloom release (`5bbfc14f98b4fc4cd5a124626174fdf54e0b0c3d`) has `AtomicBloomFilter`. Its public `insert_hash(&self, u64)` and `contains_hash(&self, u64)` directly accept prehashed input. It stores boxed atomic 64-bit words, uses relaxed atomic loads and `fetch_or`, and derives multiple probes from the source hash. `with_num_bits(B * 8).expected_items(n)` can match the native backing-byte budget while preserving the upstream probe-count policy. Report the resulting `num_hashes()` and actual slice bytes. `insert_all` hashes generic values, so use the public prehashed singleton loop for this comparison. [public atomic API generated by the shared macro](https://github.com/tomtomwombat/fastbloom/blob/5bbfc14f98b4fc4cd5a124626174fdf54e0b0c3d/src/lib.rs), [atomic storage](https://github.com/tomtomwombat/fastbloom/blob/5bbfc14f98b4fc4cd5a124626174fdf54e0b0c3d/src/bit_vector.rs).

A future actual-overlap experiment should compare `AtomicBloomFilter` with native `AtomicFastPatternBloomFilter` using the same total pinned cores, writer/reader split, input hashes, duplicate rate, allocated bytes and final independently calibrated FPR. Preload a known subset before the start barrier; readers can assert no false negatives only for that subset while writers add new keys. Queries racing an unfinished multiword insert may return absent for that key in either layout. Validate every completed key after writer join, or publish completed chunks with a separate release/acquire protocol before requiring reader visibility. Do not treat relaxed filter operations as publication of unrelated data. Avoid concurrent clear/intersection in this append-only contract. Keep serial build, parallel build, read-only queries and overlapping insert/read throughput separate, including thread-launch/barrier accounting. This is a contract proposal, not a performance result; the existing external multithread results cover immutable queries only.
