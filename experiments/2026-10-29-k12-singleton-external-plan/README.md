# C++ K12 singleton comparison proposal

This is one source-only follow-up for the unchanged K12 singleton SIMD candidate. No compiler, Bloom filter, calibration or timed workload has run for this stage. The proposed 48 processes produce 616 rows: 256 primary singleton rows and 360 native diagnostic rows. It is not a request to promote the candidate.

The completed candidate/control screen found improvements in all batch1/3 contrasts, but the large batch31 hash-inclusive path lost in all twelve observations and batch4096 was mixed. The candidate also changed compiler inlining, frame size and unrolling relative to the old public API. Those facts motivate a new same-process comparison; none of the older latencies enters this proposal's future rankings.

## Fixed panel and source identities

`derive.py` reads exact committed JSON blobs, emits the selection/ledger, and verifies them byte-for-byte on subsequent invocations. `sources.json` pins the committed tables and constructor/API sources. `selection.json` records every selection reason, the exact original constructor argument, actual backing bytes, logical bytes, allocation units, probe policy and known calibration identity. Historic null leaders and failed fresh-confirmation qualifications are retained as context. They do not exclude future data.

- Thirty external points: the union of external leaders from the exact-capacity main tables and cap16/24/32 frontier, the optimizer-visible singleton screen, and the newer K12 batch31/4096 tables. The latter supplies extra rival shapes, not evidence about singleton speed. There are seventeen small and thirteen large points.
- Sixteen production-native points: all four current production layouts at actual16/32 bpk for both sizes. Their real constructor n stays unchanged. Native inverses reproduce the exact allocation; old requested-bpk labels are not reused as actual capacity labels.
- Eighteen points for the candidate, the same old K12 public API and native Split64Range at actual16/24/32 bpk for both sizes.

The two K12 headers remain exact copies of the already tested candidate/control. Production and Range use the pinned current native source at556c05b. Future derivation must prove constructor/bitmap parity and retain exact old public query bodies; source naming isolation is allowed where required, kernel edits are not. Every selected external geometry matches exactly one committed grid record. For example, Boost's23.999... bpk entries include its tail/alignment allocation; a nominal24 label is insufficient to identify a matching object.

## Public API and timing contracts

Keep the already proved caller's two separate opportunities: generic calls use the unchanged noinline public `Lookup` helper; visible singleton loops expose the actual public one-key API to the compiler. The latter uses `ContainsHash` for K12/Range and native types where that is public, otherwise the pinned constant-one public call. FastFilter Fixed16/32/64/SimdBlock retain their existing `Lookup(1)` route to public Find. SingleV1 aliases remain real controls even if visible code folds. Rocks K8 and Batch32 retain their distinct public paths and n1 costs.

Boost alone receives the existing proved `ScalarContains` facade delegating to public `may_contain`, with the same explicit shim inline policy as the visible60 screen. Its exact-capacity constructor, Insert and batch Lookup stay byte-identical. No external private kernel shortcut or new native force-inline hint is allowed. Direct one-key and opaque generic contracts are reported separately for every owner. Actual later assembly must disclose remaining facade/cross-call costs and any folding.

The four singleton metrics are pure generic lookup, generic staged common-hash lookup, pure visible public lookup and visible fused common-hash lookup. Hash and dense output writes stay inside the corresponding clocks. Poisoning, complete validation, consumption, guards and input checks stay outside. Non-singleton diagnostics keep the two generic metrics. The four-mode Williams schedule and two-mode ABBA schedule each repeat twice. One canonical whole-input build is untimed; no build speed is claimed. Scratch allocation/lifetime and bytes are reported consistently with the existing caller.

## Fresh quality and analysis rules

Calibrate every API/geometry/seed in the first primary round with2^26 independent negative raw integers beyond the mixed-query interval. Later rows reuse only exact same-construction counts after required semantic/geometry checks. Insertion raw/hash digests and native bitmap identity must match across hit rates; mixed query/output digests must match only within the same n/seed/hit/batch across rounds and between same-mapping aliases. Hit0/100 diagnostics have their own full output validation and must not be required to match hit50 outputs. There are128 API quality records and108 proven alias-group records. Aliases share one denominator, never summed probes. Distinct seeds retain separate pointwise Wilson bounds. No historical calibration result is borrowed as a new qualification.

Main comparisons require both fresh seeds' upper bounds to satisfy the selected1%,0.1% or0.01% target and actual backing to fit16/24/32 bpk. Smaller allocations compete under larger caps. All failed, unavailable and over-cap alternatives stay in the output. For each of72 n/cap/quality/mode views, each owner selects one point using geometric mean latency over the fixed four seed/round observations; that point stays fixed in the four paired comparisons. These are explicitly descriptive same-data rankings. Candidate versus production-native and candidate versus Range are separate from candidate versus external. The all-native composite is labeled as a composite. Missing or unqualified rivals produce no qualifying win.

Also retain576 individual-cell rival-envelope records: the fastest eligible external and production-native point in each of288 seed/round views, using the same both-seed fresh quality gate. Preserve each identity, time and candidate/envelope ratio even when the point differs from the geometric-mean selection. Beating the fixed selected rival alone does not imply beating every eligible selected-panel rival in every cell. These envelopes require no additional measurements and do not weaken the quality rule.

Retain all2,304 geometry-view alternatives,288 individual views,864 named candidate/oldK12 and candidate/Range same-byte contrasts,2,032 trial vectors and16,256 trial samples. Every loss remains visible. Do not pool hit rates, batch sizes, seeds, rounds or API modes to conceal a regression. The two launch rounds share inputs and differ in environment and calibration history; they do not isolate a causal order effect. Native wins against Range alone do not establish production-native leadership, and the one candidate/control change remains coupled to compiler inline/unroll decisions.

## Required next proof, not yet authorized execution

Derive one actual public caller with all selected constructor recipes and static typed adapters. Reuse the existing timer/workload helper bodies and identify exact allowed glue changes. A focused proof must check selected allocations/probes, old public API parity at retained geometries, tiny tails/null0/guards, poison failures, all inserted positives and complete mixed outputs. In particular test native16/32 sizing and previously untested visible exact-capacity external points. Use normal, minimalAVX512F and ASan profiles only for these public paths. Capture actual ELF symbol address spans for callers and hot callees; do not trust a successful empty objdump result. No need to repeat previously proved large parallel/kernel matrices.

Before performance, freeze all actual inputs, external dependencies, tools, compiled binaries, executable command ledger and source guards. Every case must retain the exclusive socket flock in its child process and validate placement before launch. This proposal contains no build or formal-run authorization.
