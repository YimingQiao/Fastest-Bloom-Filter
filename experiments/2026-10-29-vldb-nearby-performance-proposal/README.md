# Proposed fixed raw-u32 nearby-capacity comparison

This is a source-only proposal. No worker, filter, planner, compiler or measurement has run for this stage. The completed fixed36 accuracy pilot remains unchanged at `f8d1449cb5abb41609b426229bde11f77ad03921`, with its full interpretation at `1349ebf3285c534ec56f96096d4148f8ca60a08e`.

Use one new legacy-context executable, GCC12.2/native, the complete Boost1.83 include root and the already verified native/ASan original archives. Compile only new harness translation units; never rebuild or patch the upstream library. This one executable contains every original/nearby comparison and all native references. Each row still runs in a separate fresh process, because original public tuning uses non-overwriting global entries. No Boost1.92 code enters this executable, and no old native/context correction or old latency enters its ranking.

## Fixed finite panel

Recommended panel: **20 APIs × two sizes × two caps × two launch rounds = 160 process rows**, with three query contracts per row, hence 480 mode records. Query repetitions are six balanced permutations; repeated calibration across rounds or proven U aliases is checked for exact equality and never pooled.

The public original configurations are `sector32-u1`, `sector32-u2`, `sector32-u4`, `sector64-u1`, `sector64-u2`, `sector64-u4`, and `register64-u0`. Each has two constructor policies: the unchanged original largest-fitting geometry and the already fixed nearby odd geometry. These **14 PImpl aliases** retain every U shape instead of assuming U1 represents the fastest public batch API. The new U2/U4 nearby aliases require caller parity against the proven U1 geometry before any timing; they cannot inherit quality evidence merely from a presumed equivalence.

The **six project controls** are the four unchanged Stage3 native snapshots (`FastPatternBF`, `FourSectorBloomFilter`, `Split64BloomFilter`, `ByteSplitBloomFilter`), optional native `Split64RangeBloomFilter`, and experimental `FourSectorRange12`. Range and K12 are separate ownership categories, not replacements for the production four. Every API is kept at both caps regardless of the earlier FPR failures. This is a public PImpl capacity study, not a new claim against the upstream direct-template/static surfaces or every modern external baseline.

Use 65,536 and 33,554,432 inserted keys; caps12/24 bits/key; seed42; 2^22 queries with the unchanged exact `i % 100 < 50` schedule; and 2^24 distinct nonmember calibration keys. Seed42 deliberately permits exact semantic reproduction against the existing pilot and raw728 controls. It is training/bridge evidence, not a fresh-seed confirmation. One complete build precedes query trials; construction is untimed and its metrics remain unavailable. Every inserted key is validated.

Round0 iterates sizes, caps and the exact API list in `proposal.json`; round1 reverses the entire case list. This gives each row two positions but is not a statistical randomization or a guarantee against process/order effects. All six within-process query-mode permutations remain unchanged. Do not average rounds into independent confidence claims; show both individual rows and their descriptive range.

## Geometry and caller contract

The original/nearby formulas, K8 probes, hash input and public PImpl methods remain exactly those of the completed accuracy worker. For nearby, select the single largest accepted odd divisor within the fixed top1% capacity window, charge the complete rounded backing and retain unsupported status without fallback. The rule is independent of U. Check the requested U against the constructor-captured public metadata in every fresh process. Do not change HOME or the user tuner file; fingerprint it before/after.

Production power-of-two controls retain real constructor `n`. Under cap12 they actually allocate8 bits/key; under cap24 they allocate16. Their exact constructor argument is still `NativeArgument(n, cap_bytes)`, preserving FastPattern mask density. The optional Range and experimental K12 controls use complete64-byte-line exact capacity, actually12/24 bits/key on these sizes. Their existing bitmap mapping, insertion, masks, dispatch and prefetch are unchanged. Metadata distinguishes nominal cap, logical bytes, charged backing bytes, geometry/address mode and ownership.

Re-use the byte-exact Stage3 `common.hpp`, `query_loop.hpp` and workload, including the same coarse whole-array erased boundary, typed inner query loop, dense materialization and post-timer complete-output/guard checks. Public singleton is independent-query throughput with optimizer freedom, not dependent-key latency. The contracts are:

| Family | Singleton | Dense batch1 / batch4096 | Scratch charged separately |
|---|---|---|---|
| Original/nearby PImpl | unchanged public `contains(raw_u32)` | unchanged public compact `batch_contains`, then compact-position to dense0/1 conversion **inside** the timed call | 0 / 4 / 16,384 bytes |
| Four Stage3 native controls | existing common Murmur64 of zero-extended raw_u32 + constant-one public `Lookup` | common hash into prepared scratch + unchanged native `Lookup` **inside** the timed call | 0 / 8 / 32,768 bytes |
| Optional Range and experimental K12 | common Murmur64 + existing public `ContainsHash` | common hash into prepared scratch + unchanged public `Lookup` | 0 / 8 / 32,768 bytes |

The new two wrappers can expose `ScalarContains` forwarding directly to their existing `ContainsHash`, which the unchanged Stage3 `RawHash` trait already detects. This is an explicit best-public-singleton surface. It must be recorded and inspected in assembly, not silently attributed to the layout. No private scalar access or new hash bypass is introduced. Build hash scratch for native controls remains8n bytes, outside the query timer and separately reported. Object/control/global tuner heap and bitmap allocation remain separate categories; this comparison does not claim total RSS.

The optional Range source is pinned to `81f40f16caa44586537d577f998c33fec4c22be8` (`include/split64_range_bloom.h`, its size helper and unchanged base closure). K12 is pinned to the actual-caller proof `e150be33b95a22dca9b75175e6174b9555c82393`, using `experiments/2026-10-29-four-sector-range12-screen/four_sector_range12.h` and its frozen include closure. Use a local derived copy of the complete K12/base/sizing header closure with the **single namespace identifier** `bloom_filters` changed to `nearby_k12`, plus explicit local include routing. Record the exact source blobs, replacement script and resulting patch. There is no change to expressions, masks, constants, dispatch, layout, constructor calculation or method bodies. Its raw wrapper constructs `nearby_k12::RangeBytes{cap_bytes}`; production Range uses its original `bloom_filters::RangeBytes{cap_bytes}`. Full bitmap/output oracle comparison binds namespace-only copies to their original types. No preflight is inferred from this proposal.

The existing original aliases retain exact prior semantic observations. Public metadata must show the requested U; no scalar0/1 relabeling is permitted. 5. Retain the old public allocation accounting and add a bounded check of actual backing plus exact prepared scratch for the changed capacities and new wrappers. There is no new allocator/instrumentation inside the performance binary. Do not reuse the old4096-byte control figures as measured large-allocation totals.

The scalar public call and hash/conversion must lie within the existing whole-array clock boundary. Keep all public out-of-line PImpl costs; do not replace them with private kernels to improve the result.
